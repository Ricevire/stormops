# ADR-003 指标分链路：6 小时内存，90 天 VictoriaMetrics

- 状态：已采纳
- 日期：2026-11-23
- 决策者：平台负责人

## 背景

平台自己产生指标（被监控对象的状态），同时也展示指标。问题是：**同一份指标，在不同时间尺度上应该从哪里读？**

时间尺度跨度很大：

| 场景 | 窗口 | 特点 |
| --- | --- | --- |
| 控制台「现在怎么样」 | 实时 | 要快，要准 |
| 控制台「最近 6 小时的曲线」 | 分钟级粒度 | 要能画图，点数不能太多 |
| 「上周三下午磁盘是多少」 | 小时级粒度 | 要能回溯 |
| 「这个月增长了百分之多少」 | 天级粒度 | 要能聚合 |

约束：2 GB 内存、40 GB 磁盘、5 Mbps 带宽。

## 决策

**两条读取路径，以 6 小时为界。**

```
写入：
  stormagent ──POST──► StormOps 内存环（6h，30s 间隔）
                            │
                            └──► /metrics ──► vmagent ──► VictoriaMetrics（90d）

读取：
  窗口 ≤ 6h   ──► StormOps 内存（/api/v1/*）
  窗口 > 6h   ──► VictoriaMetrics（/api/v1/query_range 代理）
  按天聚合    ──► PostgreSQL（每日 03:20 全量重建）
```

## 理由

### 为什么 6 小时

控制台上所有图表的窗口都在 6 小时以内（1h / 3h / 6h）。超过 6 小时的查询全部归到「容量规划」页，那页的数据源是 PostgreSQL 的日粒度快照。

所以 6 小时是**根据 UI 的实际最大窗口反推出来的**，不是拍的。

内存成本：6 小时 / 30 秒 = 720 个点/指标/主机。4 台主机 × 约 10 个指标 × 720 点 × 16 字节 ≈ 460 KB。可以忽略。

### 为什么不用 VictoriaMetrics 直接承担所有查询

技术上可行，但有三个问题：

1. **延迟**：控制台首屏要查多个接口（概览、资产、告警、容量）。如果每个都走 HTTP 到 VM 再解析 PromQL 结果，首屏会明显变慢。
2. **可用性耦合**：VM 挂了控制台就白了。而控制台是运维排障的入口，它不应该依赖被观测系统。
3. **写入延迟**：vmagent 是 15 秒抓一次，意味着 VM 里的数据最多滞后 15 秒。控制台显示「当前 CPU 87%」时，运维期望的是「现在」，不是「15 秒前」。

第 3 点最实际。用 VM 做实时查询，会出现「控制台显示正常，但机器已经挂了 10 秒」的窗口。

### 为什么不用自研 TSDB

考虑过。否决理由：VictoriaMetrics 单机版 57 MB 内存、零配置、支持 PromQL、压缩比极高。自己写一个能达到同等压缩和查询能力的 TSDB，是几个月的工程量，且必然有 bug。

**用别人的成熟存储，用自己的采集和判定逻辑** —— 这条线划在「数据怎么产生」和「数据怎么存」之间。

### 为什么 PostgreSQL 只做日粒度

分位数（P95）、排行榜（TopN 攻击 IP）、回归（`regr_slope`）这类查询，SQL 写出来 10 行，Go 里写 200 行且容易错。

但 PostgreSQL 不适合存原始指标：

- 40 GB 磁盘，原始指标 30 秒一个点，几天就写满
- 高频写入对 2C2G 的 IO 压力大

所以只存**每天一个快照**（`ops.capacity_snapshot` 是每天一条/卷），配合 `TRUNCATE + COPY` 全量重建。数据量小，查询快，且天然可重放。

## 后果

### 好的

- 控制台首屏不依赖任何外部服务
- 实时查询延迟在微秒级
- 长期存储成本极低（VM 压缩后 90 天数据在百 MB 级）
- 分析类查询用 SQL，可读性和正确性都高

### 坏的

- **两条路径的数据可能不一致。** 内存里 6 小时的点是 agent 直报的，VM 里的是 vmagent 抓 `/metrics` 得到的。如果 `/metrics` 的聚合逻辑和内存里的样本聚合方式不同，同一个时间点在两边会显示不同的值。
  当前缓解：`/metrics` 直接从内存环导出，两者同源。但这是约定，不是强制。
- **6 小时的边界是硬的。** 查 6 小时零 1 分钟会切到 VM，粒度和口径都会变。UI 上已经在图表标题里标注了数据源，但仍然会让用户困惑。
- **VM 断档无人知。** 如果 vmagent 挂了，vmalert 查不到数据，规则返回空而不是报错，**告警不会触发**。「没数据」被当成「没问题」。
  这是当前最需要补的一个洞：必须加 `absent()` 规则。
- **PostgreSQL 有最多 24 小时延迟。** 昨天的数据要等今天 03:20 才能查到。对容量规划够用，对故障复盘不够。

### 待补

```yaml
# 应该加但还没加的规则
- alert: MetricsPipelineBroken
  expr: absent(stormops_host_cpu_pct) or absent(up{job="stormops"})
  for: 3m
  labels:
    severity: critical
  annotations:
    summary: "指标链路断档，当前所有监控结论都不可信"
```

`absent()` 是这里的关键。没有它，监控系统最危险的失效模式（静默失效）就没有防护。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| 全部走 VictoriaMetrics | 首屏变慢、15s 写入延迟、VM 挂了控制台白屏 |
| 全部走内存 | 无法回溯超过 6 小时 |
| 全部走 PostgreSQL | 高频写入压力大，40 GB 磁盘撑不住原始指标 |
| Prometheus 替代 VM | VM 内存占用更低、压缩比更好，2C2G 上更合适 |
