# ADR-001 状态存储：内存 + 原子落盘 JSON

- 状态：已采纳
- 日期：2026-11-23
- 决策者：平台负责人

## 背景

StormOps 需要保存一份可变状态：CMDB 台账、服务定义、告警规则、活跃告警、静默、发布记录、WAF 规则、最近 5000 条攻击事件、6 小时指标样本。

规模估算：

| 数据 | 量级 | 增长 |
| --- | --- | --- |
| 资产 / 服务 | 十级 | 极慢 |
| 告警规则 / WAF 规则 | 十级 | 极慢 |
| 活跃告警 | 个位数 | 随故障波动 |
| 指标样本（6 小时，30s 间隔） | ~720 条/主机 | 有界 |
| 攻击事件 | 上限 5000 条 | 有界（环形截断） |
| 发布记录 | 百级 | 慢 |

总量在 MB 级，且有明确上界。

约束：

- 部署在 2C2G 机器，磁盘 40 GB
- 单二进制 `scp` 上去就能跑，不要额外的初始化步骤
- 控制台必须秒开，不能被磁盘 IO 拖住

## 决策

**状态全部驻留内存，后台每 3 秒异步落盘到一个 JSON 文件。**

```go
st.View(func(s *model.State) { ... })   // 读锁
st.Update(func(s *model.State) { ... }) // 写锁 + 标记 dirty
```

落盘用「写临时文件 → fsync → rename」：

```
state.json.tmp → fsync → rename → state.json
                              ↘ state.json.bak（旧文件）
```

启动时：`state.json` → 解析失败则 `state.json.bak` → 都失败才用配置初始化。

## 理由

### 为什么不用 SQLite

SQLite 是这种场景的常规答案，但在这里代价大于收益：

1. **部署形态**：SQLite 需要一个可写 db 文件 + WAL 文件 + 需要考虑 `journal_mode`、`busy_timeout`、并发写锁。而 JSON 方案下，运维理解的模型就是「一个文件，坏了就换一个」。
2. **性能不是瓶颈**：所有查询都在内存里做，SQLite 在这里唯一的价值是「不用自己写序列化」，而 `encoding/json` 已经够了。
3. **不利于后续演化**：真正上量之后要换的是 PostgreSQL 或 VictoriaMetrics，不是 SQLite。中间加一层 SQLite 只是多一次迁移。

### 为什么落盘间隔是 3 秒

- 1 秒：写放大明显，2C2G 上每秒钟一次 `fsync` 会跟其他服务抢 IO
- 3 秒：进程被 `kill -9` 最多丢 3 秒数据。而指标本身是可重采的，攻击事件丢了也只是少几条审计记录 —— **这些数据的价值不足以支撑更频繁的 fsync**
- 10 秒以上：用户改了 WAF 规则，10 秒内重启就丢了，体感上是「平台不保存设置」

3 秒是「数据价值」和「IO 成本」的交点。

### 为什么用 rename 而不是直接覆写

直接 `os.WriteFile(state.json, ...)` 在断电/被杀时会留下一个**合法的、空的或截断的** JSON。下次启动解析出空状态，CMDB 被清空 —— 这是最坏的一种失败，因为它安静地发生。

`rename` 在同一个文件系统上是原子的：要么是旧文件，要么是新文件，不存在中间态。

### 为什么读不到就回退 `.bak`

`rename` 保证单文件原子，但不保证「新文件内容正确」。如果序列化逻辑有 bug，写出了结构合法但内容错误的数据，`.bak` 是最后一道防线。

代价是磁盘上多一份状态，MB 级，可以忽略。

## 后果

### 好的

- 控制台所有查询都是内存操作，P99 在微秒级
- 部署极简：一个二进制 + 一个配置 + 一个状态文件
- 故障可理解：状态坏了就是「换文件」，不需要 `sqlite3 .recover` 之类的技能
- 状态文件可以直接 `jq` 查看，排障时很方便

### 坏的

- **单点**：状态只在这一台机器上，没有副本
- **`kill -9` 丢 3 秒**：可接受，但必须知道
- **无法水平扩展**：多实例会各自持有一份状态，互相覆盖
- **量级天花板**：JSON 全量序列化在十万级对象时会明显变慢（每次写都是全量）

### 什么时候该换掉

触发条件（任意一条）：

1. 攻击事件保留量需要超过 5000 条
2. 资产数量超过 1000
3. 需要多实例部署
4. 落盘耗时超过 100 ms

换的目标不是 SQLite，而是 **PostgreSQL 做主存 + 内存做缓存**，`store` 的 `View`/`Update` 接口可以保持不变，只换实现。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| SQLite | 部署复杂度和后续迁移成本高于收益 |
| PostgreSQL 直存 | 让在线读路径依赖外部进程，PG 挂了控制台就打不开；与「控制台必须始终可用」矛盾 |
| 纯内存不落盘 | 重启后 CMDB 全丢，WAF 规则回退到默认，不可接受 |
| etcd | 2C2G 上多跑一个 Raft 集群，为一个单机平台付出这个代价没有意义 |
