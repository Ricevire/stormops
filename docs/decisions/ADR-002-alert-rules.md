# ADR-002 告警规则：双引擎并存，配置单向导出

- 状态：已采纳
- 日期：2026-11-23
- 决策者：平台负责人

## 背景

告警判定放在哪里，有三种做法：

1. **只在 StormOps 内部做**（自己写规则引擎，内存数据直接判定）
2. **只在 vmalert 做**（PromQL 规则，数据从 VictoriaMetrics 查）
3. **两边都做，各管一段**

约束：

- 控制台需要秒级反映状态变化（运维盯着看的时候，改一条规则应该立刻看到效果）
- 告警需要能外发（IM、电话），需要分组、抑制、静默，这些 Alertmanager 已经做得很成熟
- 告警需要能回溯（「昨天下午三点的这条告警，当时的值是多少」）
- 机器只有 2C2G，不能为了告警再堆组件

## 决策

**采用方案 3，并规定单向同步：以 StormOps 的规则为唯一真相源，vmalert 规则文件由 API 导出生成。**

```
StormOps 规则（JSON，运维可改）
        │
        ├──► 内部引擎：内存数据，1s 内判定，驱动控制台 UI
        │
        └──► GET /api/v1/export/vmalert
                    │
                    ▼
             rules.yml（PromQL）
                    │
                    ▼
             vmalert → Alertmanager → 外发
```

## 理由

### 内部引擎不可替代的部分

控制台的「告警」页需要在**规则改动的下一秒**就反映新状态。

如果只靠 vmalert：改一条规则 → 写文件 → `curl -X POST /-/reload` → 等下一个 `interval: 30s` → 再等 `for: 2m`。最坏情况 2.5 分钟后才看到效果。运维会以为「改了没用」，然后反复改。

内部引擎直接在内存数据上跑，改完下一次 `evalLoop`（1 秒）就生效。

另外一个细节：控制台的告警条目带有「当前值」「触发时间」「所属规则」这些字段，需要和 UI 的其他数据（资产、服务）在同一个事务视图里读出来。跨系统拼装会有一致性问题 —— 比如告警说 `media-nas-01` 磁盘 86%，但资产页显示这台机器已经下线了。

### vmalert 不可替代的部分

1. **回溯**：内部引擎只有 6 小时内存数据。要回答「这条告警一周前触发过几次」，必须有长期存储。
2. **`for` 语义的严谨性**：vmalert 的 `for: 2m` 是基于真实时间序列的连续判定；内部引擎因为数据在内存环里，窗口是近似的（见下文「后果」）。
3. **分组抑制**：Alertmanager 的 `group_by` / `inhibit_rules` / `silence` 是成熟的，重写一遍没有意义。
4. **外发通道**：飞书、钉钉、PagerDuty 的集成都现成。

### 为什么单向而不是双向

双向同步（两边都能改，互相覆盖）会产生一个经典问题：**冲突时以谁为准？**

选单向的理由很实际 —— 运维改规则的地方只有一个（控制台/API），`rules.yml` 是产物不是源文件。这样：

- 不会出现「有人手改了 rules.yml，下次导出被覆盖」的困惑
- 不需要做 diff 合并
- 规则版本可以跟 StormOps 的状态文件一起备份

代价：想改告警必须通过 StormOps，不能直接改 YAML。这对一个单机平台来说是合理的限制。

## 后果

### 好的

- 控制台秒级反馈，改规则即时可见
- 告警可回溯、可外发、可抑制
- 规则只有一个真相源，不会两边不一致
- 少一个组件（不需要单独的规则管理服务）

### 坏的

- **两套规则要维护。** 新增一条规则要同时考虑 JSON 描述和 PromQL 表达。当前靠导出接口生成，但导出的 PromQL 需要人工 review（见 `deploy/vmalert/rules.yml` 头部注释）。
- **内部引擎的 `for` 是近似的。** 数据在内存环里，`breachSustained` 用了 `0.8 * forSec` 的容差，避免采样抖动导致永远凑不满时长。这是个妥协，不是精确实现。
- **`rules.yml` 需要重启或 reload vmalert 才生效。** 导出是手动的，没有做成自动推送 —— 因为 vmalert reload 会让正在 `for` 中的告警计时重置。
- **Receiver 是 `devnull`。** 当前没有配真实 webhook，避免把测试告警发到真实群里。这意味着告警实际上没有「通知到人」，只有一个可查的 active 列表。上线前必须替换。

### `devnull` 这件事要单独说

`alertmanager.yml` 里：

```yaml
receivers:
  - name: devnull
```

这不是忘了配，是刻意的：在没有真实值班表和 webhook 地址的情况下，配一个假的 webhook 会让「告警链路已打通」这个结论变得可疑（到底通了没有？）。

`devnull` 的语义是明确的：**告警能送到 Alertmanager，但没有人被通知。** 这个状态是诚实的，也明确指出了下一步该做什么。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| 只做内部引擎 | 没有回溯、没有分组抑制、外发要自己写 |
| 只做 vmalert | 控制台反馈延迟 2.5 分钟，改规则的体验不可接受 |
| 双向同步 | 冲突解决成本远高于收益 |
| 用 Grafana Alerting 统一 | 又多一个组件，2C2G 上不划算；Grafana 的告警也是基于 PromQL，解决不了内部引擎要解决的问题 |
