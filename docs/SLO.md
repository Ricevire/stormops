# SLO 与错误预算

SLO 的价值不在于"写一个 99.99%"，而在于**逼着自己回答：这个数字怎么算出来的、超了之后停什么**。

本文件定义 StormOps 承载的三类对象：业务站（stormsite）、运维平台自身（stormops）、监控链路（VM 栈）。三者的可用性要求和失败代价完全不同，所以不能用同一个口径。

---

## 1. 服务分级

| 级别 | 对象 | 挂了会怎样 | 目标 |
| --- | --- | --- | --- |
| P0 | 业务站 `stormsite`（经 Nginx） | 官网/课程站打不开，外部可见 | 99.9% / 月 |
| P1 | 监控链路（vmagent → VM → vmalert → AM） | 出问题没人知道，故障发现时间从分钟级退化到"客户投诉" | 99.5% / 月 |
| P2 | StormOps 控制台与发布能力 | 运维只能手工上机器操作，效率退化但业务不受影响 | 99.0% / 月 |

注意 P0 和 P2 的关系：**StormOps 挂掉不影响 P0 的可用性目标，但会拉长 P0 的恢复时间**。因为 WAF 判定走的是 fail-open 分支（见 ADR-004），业务流量不受阻，但此时没有 WAF 保护。

---

## 2. SLI 定义

指标必须是可采集的，否则就是口号。

| SLI | 定义 | 数据来源 | 当前实现 |
| --- | --- | --- | --- |
| 可用性 | `1 - (5xx 请求数 / 总请求数)` | Nginx access log 聚合 | ⚠️ 未接入，当前用合成探测代替 |
| 合成可用性 | 探测 `/healthz` 成功的比例 | `stormops_svc_up` | ✅ 已实现，30s 一次 |
| 延迟 | `/healthz` 的 P95 响应时间 | 探测侧记录 | ⚠️ 只采到 up/down，未采耗时 |
| WAF 判定延迟 | `/internal/waf/check` 的 P99 | StormOps 内部计时 | ⚠️ 未导出 |
| 告警及时性 | 指标异常到告警 firing 的间隔 | 规则 `for` + 抓取间隔 | ✅ 可推算：15s 抓取 + 30s 评估 + for |

**诚实说明**：目前只有「合成可用性」是完整闭环的，其余三项是设计好了但没接。这不是遗漏，是排序 —— 在只有一个业务站的情况下，先把「站挂没挂」这个问题回答清楚，比先做延迟分位数更有价值。

接入顺序应当是：Nginx 日志聚合 → 探测耗时 → WAF 判定 P99。前两个决定了 P0 的 SLI 是否可信。

## 3. 错误预算

月可用性 99.9% 对应：

```
30 天 × 24 h × 60 min = 43200 min
允许不可用 = 43200 × 0.1% = 43.2 min/月
```

43 分钟听起来很多，但要扣掉计划内变更：

| 项目 | 预算消耗 | 说明 |
| --- | --- | --- |
| 计划内发布 | 0（设计上应为 0） | 发布走 `switch` 软链，理论无中断 |
| 发布失败回滚 | 每次 10–30 s | `health` 3 次探测 + 回滚 + 再确认 |
| Nginx reload | < 1 s | 平滑 reload，不断连接 |
| 内核/依赖升级 | 需重启，1–3 min | **必须走变更窗口，且计入预算** |

结论：每月可用于「计划外故障」的预算实际约 35 分钟。

### 预算消耗后的动作

这是 SLO 真正的用处，必须提前约定：

| 剩余预算 | 动作 |
| --- | --- |
| > 50% | 正常按需求排期 |
| 20%–50% | 暂停非必要变更，优先补监控盲区 |
| < 20% | **冻结功能变更**，只允许修复类提交 |
| 已耗尽 | 停止一切变更，做一次完整复盘，产出至少一项自动化防护 |

「冻结」这条如果不敢写，SLO 就是装饰品。

## 4. 告警分级与响应

| 级别 | 触发条件 | 响应时限 | 通知方式 |
| --- | --- | --- | --- |
| P1 | `ServiceDown` 持续 1 min、`StormOpsDown` | 15 min 内响应 | 立即（电话/IM @所有人） |
| P2 | `HostDiskHigh` > 85%、`HostMemoryHigh` > 90% | 4 h 内处理 | IM 群 |
| P3 | `WAFBlockSpike`、容量预测 < 45 天 | 下一个工作日 | IM 群，不 @ |
| P4 | 单条 WAF 规则日志命中、容量 < 90 天 | 周会过一遍 | 仅进控制台 |

分级依据是**「不处理的后果有多快兑现」**，不是「看起来严不严重」。磁盘 86% 是 P2 而不是 P1，因为它还有几天的缓冲；`ServiceDown` 是 P1，因为用户此刻就打不开。

### 抑制规则

Alertmanager 里配了一条：同 host 的 `critical` 抑制 `warning`。

```yaml
inhibit_rules:
  - source_matchers: [severity="critical"]
    target_matchers: [severity="warning"]
    equal: [host]
```

原因很实际：一台机器磁盘满了，会同时触发磁盘告警、服务不可用告警、可能还有内存告警。如果不抑制，值班的人会收到一串通知，其中只有一条是根因。抑制之后，先看到的是最严重的那条，顺着它查就行。

## 5. 当前达成情况

基于这台服务器 2026-11-23 起的运行数据（样本量小，仅作基线）：

| 指标 | 数值 | 备注 |
| --- | --- | --- |
| 合成可用性 | 100% | 探测间隔 30s，暂无失败样本 |
| 平均恢复时间（MTTR） | 无样本 | 尚无生产故障 |
| 变更失败率 | 首轮部署 1 次失败 | 见 [PM-003](postmortem/PM-003-vmalert-restart.md)，原因是装错二进制 |
| 告警准确率 | 演示数据下 100% | 生产数据下未知，需要积累 |

**样本量不足是这份 SLO 最大的问题。** 真实的 SLO 需要至少一个月的连续数据才有意义，当前只能作为「口径定义」使用。这一点在面试时应当主动说明，而不是拿 100% 当成绩。
