# 容量规划

## 1. 为什么不用「使用率告警」就完事

「磁盘超过 85% 告警」是最常见也最没用的一种容量管理。

对媒体业务来说，问题从来不是「现在满了没有」，而是**「还有几天拍不了片」**。

一台 200 TB 的 NAS，从 85% 涨到 95% 可能只要 9 天（日增 100 GB 级）；也可能要 3 个月（日增几 GB）。同样是 85%，处理紧迫性差 10 倍。使用率告警把这两种情况压成同一个通知，等于没有信息量。

所以容量模块的输出是三件事：

1. **增长速率**（GB/天）
2. **剩余天数**（按当前速率）
3. **这个预测可不可信**（R²）

第 3 点最容易被忽略，但它决定了前两个数字能不能用。

---

## 2. 算法

`internal/capacity` 用最小二乘线性回归：

```
slope     = Σ((x - x̄)(y - ȳ)) / Σ((x - x̄)²)
intercept = ȳ - slope · x̄
R²        = 1 - SS_res / SS_tot
```

其中 `x` 是「距该卷第一天过了多少天」，`y` 是已用字节数。

`R²` 的含义：**增长有多接近一条直线**。

| R² | 判定 | 处理 |
| --- | --- | --- |
| > 0.95 | 可信 | 直接按 `DaysLeft` 排采购 |
| 0.80–0.95 | 参考 | 结合业务口径看，比如是不是有集中导入 |
| < 0.80 | 不可信 | 不用这个数字下决策，先查为什么非线性 |

R² 低通常意味着三种情况之一：数据点太少（卷刚接入）、有台阶式增长（批量导入）、或者采集有断档。这三种都不该用回归结果做采购决策。

### 输出字段

```go
type CapacityForecast struct {
    Volume       string  `json:"volume"`
    Capacity     float64 `json:"capacity"`
    Used         float64 `json:"used"`
    UsedPct      float64 `json:"usedPct"`
    SlopePerDay  float64 `json:"slopePerDay"`
    R2           float64 `json:"r2"`
    DaysLeft     int     `json:"daysLeft"`
    RunwayDate   int64   `json:"runwayDate"`   // Unix 秒
    Projected30  float64 `json:"projected30"`
    Status       string  `json:"status"`
}
```

`RunwayDate` 输出成时间戳而不是「N 天后」，是因为采购流程要填的是日期，不是天数。

## 3. 双判据定级

```go
if usedPct >= critPct || (daysLeft >= 0 && daysLeft < 14) {
    return "critical"
}
if usedPct >= warnPct || (daysLeft >= 0 && daysLeft < 45) {
    return "warn"
}
return "ok"
```

为什么两个判据都要：

- 只看天数：漏掉「水位 96% 但已停止增长」的卷。它不会撞线，但已经没有写入余量，一次临时导出就能写满。
- 只看水位：漏掉「才 60% 但日增 2%」的卷。按天数算只剩 20 天，但水位看起来还很安全。

阈值选 14 天和 45 天，对应的是**采购和上架的物理时间**：企业级硬盘从下单到上架通常 1–2 周；如果要在撞线前留出数据迁移窗口，需要 45 天以上开始走流程。这两个数字不是拍脑袋，是流程倒推出来的。

## 4. 真实结论（2026-11-23）

```sql
 volume | current | growth_per_day |  r2   | days_to_20tb |      confidence
--------+---------+----------------+-------+--------------+----------------------
 素材库 | 17 TB   | 108 GB         | 1.000 |           11 | 可信（增长接近线性）
 备份卷 | 4128 GB | 24 GB          | 1.000 |          596 | 可信（增长接近线性）
```

读法：

- **素材库当前 17 TB，日增 108 GB，R² = 1.000。** 增长是严格线性的，说明这是稳定的拍摄-回传节奏，不是偶发导入。按这个速率 **11 天**后撞 20 TB 红线。
- **备份卷 4 TB，日增 24 GB，还有 596 天。** 完全不用管。

R² = 1.000 值得警惕而不是高兴。真实世界的存储增长几乎不可能这么完美，出现 1.000 说明这批数据来自规律性生成（当前是演示数据），不是真实采集。**换成真实数据后必须重新算 R²，再决定要不要信这个 11 天。**

这一点是刻意写进文档的：拿一个 R² = 1.000 的漂亮数字去汇报，比拿一个 R² = 0.6 的难看数字危险得多。

### 14 天日增量（找异常导入）

```sql
 volume |    day     | daily_growth |  ma7   | flag
--------+------------+--------------+--------+------
 素材库 | 2026-11-23 | 155 GB       | 110 GB |
 素材库 | 2026-11-22 | 37 GB        | 106 GB |
 素材库 | 2026-11-20 | 145 GB       | 106 GB |
 素材库 | 2026-11-19 | 131 GB       | 108 GB |
 ...
```

单日 155 GB 对比 7 日均值 110 GB，是 1.4 倍，没到 2 倍阈值所以没标「异常增长」。但 37 GB 的低谷和 165 GB 的高峰并存，说明日增量波动在 ±50% 量级 —— 这对容量规划很重要：**按均值算剩余天数，实际可能提前 30% 撞线**。

所以真正的采购决策应该用 P90 日增而不是均值。当前实现用的是均值，这是一个已知偏差。

## 5. 数据集市

控制台能给「当前状态」和「6 小时内的图」，给不了趋势归因。所以每天 03:20 把状态全量导进 PostgreSQL：

```
stormops -export-csv /var/lib/stormops/pgexport
   → assets.csv / services.csv / releases.csv / waf_audit.csv / capacity.csv
   → TRUNCATE + \copy
   → ANALYZE
```

### 为什么全量重载而不是增量

数据量在万级，全量 `TRUNCATE + COPY` 比增量对账简单一个数量级，而且**天然具备「任意时刻可重建」的能力** —— 加载脚本写错了，改完重跑就行，不需要修数据。

代价是每天有一段数据真空（03:20 前后的变更会等到第二天）。对容量分析这种以「天」为粒度的场景，无所谓。

### 时间窗选择

03:20 是媒体业务最低谷：素材回传停了，转码队列基本空。此时 `TRUNCATE` 不会和在线查询抢锁。

`Persistent=true` 保证机器重启错过后会补跑一次，`RandomizedDelaySec=300` 避免和其他定时任务撞在同一秒。

## 6. 局限

1. **线性假设。** 素材增长不是线性的，一部剧开机和杀青之间能差 5 倍。当前实现没有做季节性分解，只能靠 R² 提示「这个预测别太当真」。
2. **均值而非 P90。** 上面已经说明，按均值排采购会偏乐观。
3. **单卷独立预测。** 没有考虑「素材库扩容后备份卷会跟着涨」这种级联关系。
4. **不预测 IOPS 和带宽。** 只做了容量（字节），没有做吞吐。5 Mbps 上行对素材回传其实是个更紧的约束，当前只有 `stormops_host_bandwidth_mbps` 的观测，没有预测。

第 4 条是这份文档里最该补的：对媒体公司来说，**带宽比磁盘更容易先撞墙**。
